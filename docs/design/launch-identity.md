# Durable launch identity

Cancellation commits its admission fence before starting the bounded provider wait. Storage failures reject the request instead of returning an acknowledgement without a durable fence. Terminal termination evidence must postdate the confirmed provider handoff (`handedAt`), not just FIFO acceptance; missing handoff evidence stays unknown.

Automation may opt into `launchId` on session creation and `deliveryId` on prompt delivery. Tokens are opaque, case-sensitive, 1–128 ASCII characters, starting with a letter or digit and otherwise containing letters, digits, `.`, `_`, `:`, or `-`. Existing browser and Oracle calls omit both fields and retain their existing behavior. This is a capability-gated transport contract, not an enabled scheduler or a new UI feature.

The owning computer commits `launchId → sessionId` in the same owner-only session-store transaction that creates the session. Concurrent retries return the existing session. Conversation replacement carries that authority to the replacement; deletion retains a tombstone rather than allowing a second launch. Providers on one computer share creation arbitration; tokens on distinct computers are independent. Session-store startup phases load this metadata; no new background service or environment flag is introduced.

Identified prompt delivery uses the existing durable FIFO and provider admission/acceptance machinery, not a second dispatch queue. The transaction accepting the queue item also stores `{deliveryId, sessionId, acceptedAt, state, promptId}`. Re-delivery returns that receipt without changing the prompt or enqueuing it again. A delivery token already belonging to another session is refused. Identified roots do not steer or replace drafts, and cannot simultaneously acknowledge an unrelated recovery token. Acceptance means the owner has taken responsibility, not that the provider has completed the work. Queue claims bind the root user/assistant identities when available; provider acceptance and terminal outcomes update the same receipt. An uncertain handoff remains accepted/unknown, protected by existing recovery markers, and is never automatically submitted again.

`GET /node-api/launches/:launchId` is node-token authenticated; the hub exposes `GET /api/computers/:computerId/launches/:launchId` with its standard Host/Origin checks and `Cache-Control: no-store`. Both return `{launch: null}` for an unknown token, otherwise the owning session/status, receipt states, known root outcomes, and any durable termination acknowledgement. Offline/failed queries are errors, never evidence that a launch does not exist. `ComputerManager.reconcileLaunch` and `SessionLauncher.reconcileLaunch` use this authority without opening a session.

`POST .../sessions/:sessionId/cancel-with-ack` (both transports), `ComputerManager.cancelWithAck`, and `SessionLauncher.cancelWithAck` are distinct from the existing signal-only `cancel`. They durably fence further prompt admission, discard queued followers with rejected/stopped receipts, request provider/background cancellation, and wait for evidence. The fence survives restart and remains set after acknowledgement; use a new launch for new work. The bounded wait defaults to 10 seconds, accepts 0–30 seconds, and returns `outcome: "unknown"` on timeout or unavailable proof. Only a provider-proven stop is persisted and returned as `"stopped"`; callers must retain their concurrency slot for `"unknown"`, reconcile, and retry cancellation rather than relaunching.

| Provider | Evidence required for `stopped` | Limits |
| --- | --- | --- |
| Copilot SDK | No pending admission, foreground turn, or queue dispatch; a current foreground completion in the provider event log at least as recent as the admitted prompt; supported background-task enumeration reports no running/queued tasks after cancellation. | An abort RPC, an idle store projection, missing/stale event logs, or unsupported task enumeration is insufficient and returns unknown. |
| Copilot tmux | The same fresh foreground lifecycle and background-task evidence, with the durable native queue fenced and no in-flight native handoff. | Sending the interrupt key or observing a composer does not prove termination. Native logs do not yet bind a terminal outcome to an exact queued root; that root outcome remains unknown. |
| Claude | Abort is requested, starting/registered queries and admissions are joined, and iterator teardown can establish foreground quiescence. | Full acknowledgement remains unknown even after foreground teardown: this adapter does not yet consume the provider's background-task membership and termination signals. The caller must not release its concurrency slot on iterator teardown alone. |

Every acknowledgement declares `scope: "provider-owned"`: no provider can prove the termination of arbitrary detached shell processes or external work. Session idleness alone is never treated as root success. Copilot root completion follows foreground lifecycle events; Claude root completion follows its explicit result. Updated nodes advertise `supportsLaunchIdentity` on their providers. Requiring identity, reconciliation, or acknowledged cancellation on an older computer fails with HTTP 409 and “Update this computer”; there is no silent fallback to an unidentified launch. Rollback preserves the existing state format and queue recovery protections, but older runtimes do not understand the admission fence and must not run automation that depends on it.
