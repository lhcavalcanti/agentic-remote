# Oracle lifecycle inbox

This document describes the first staged implementation for [issue #408](https://github.com/lhcavalcanti/agentic-remote/issues/408).
The [consolidated lifecycle design](../superpowers/specs/2026-10-17-oracle-proactive-lifecycle-design.md)
preserves and updates design PR #409 alongside this implementation in PR #434.
This increment adds an uninstantiated, hub-local durable inbox; it does not make
Oracle proactive and does not deliver a notice.

## Boundary

`ManagerProactiveInbox` is an internal single-writer reducer. Nothing in this
increment wires it into the application, a model turn, notifications, an
outbox, settings, quiet hours, memory, voice, or session actions. The intended
future integration must explicitly supply:

- a trusted, durable computer generation (the registered pairing generation,
  not an observation or runtime `registrationId`), captured when the session
  is read rather than when it is observed;
- an owner-issued monotonic session revision;
- a real adapter that owns observation cadence and calls `bindComputer` when a
  pairing generation changes, at the latest before pending evidence is
  delivered or its outcomes are recorded.

Without those authorities the inbox must remain unused.

## API

```ts
const inbox = new ManagerProactiveInbox(directory, {
  hubId,
  enabled: false,
  now,
})

await inbox.initialize()
await inbox.bindComputer(computerId, computerGeneration)
await inbox.observe({
  computerId,
  computerGeneration,
  sessionId,
  revision,
  origin,
  status,
  queuedCount,
  hasPendingRequest,
  isOpen,
  recovering,
})
const events = inbox.pending(20)
await inbox.acknowledge(ids, disposition)
await inbox.prune()
```

Observations contain only bounded IDs, `SessionStatus`/`SessionOrigin`,
revisions, lifecycle flags, counters, and timestamps generated by the store.
Unknown fields, malformed IDs, stale generations, and invalid counters are
refused before a state publication. Only `origin: 'manager'` is eligible.
The first observation is a baseline. A running baseline opens task generation
1; an active task produces one `failed` or `finished` event when its guards
permit it. Waiting, queued input, pending requests, closed sessions,
suspension, and recovery do not fabricate a completion.

`pending(limit)` returns a detached snapshot, prioritizing failures before
finishes and never acknowledging by reading. `acknowledge` accepts only named
events and uses one of `handled`, `irrelevant`, `superseded`, or `expired`.
Validation is all-or-nothing; identical repeated acknowledgments are
idempotent and a conflicting disposition is refused. Observation shape failures
use the typed `400 INVALID_INPUT` boundary rather than exposing arbitrary
field values.

## Durability and ownership

The state lives in a private `0600` JSON file beneath a `0700` directory.
Initialization verifies directory ownership, secures an existing owned
directory, synchronizes directory ancestry, and shares one load across
concurrent callers. Enabled storage requires POSIX UID checks and directory
sync support; unsupported hosts fail closed. Mutations refuse directory
replacement rather than silently recreating storage.
Each mutation clones a candidate state inside the serialized writer queue,
validates bounds and canonical SHA-256 namespace/event identities, writes an
exclusive `0600` pending file, synchronizes it, atomically renames it, and
synchronizes the directory before publishing the candidate to readers.
Pending evidence is never evicted. Capacity, corruption, foreign-hub,
symlink, oversize, and uncertain-rollback failures are explicit and
fail-closed. An uncertain rollback poisons that instance until a new instance
revalidates the on-disk state.
Queued inputs are detached from caller mutation before admission. Recovery
removes only recognized owned regular staging files and synchronizes their
deletion before succeeding, including a retry with no remaining staging files.

Only one trusted hub owner may write a directory. The store does not provide
multi-user authorization or a generic transaction framework. A changed
computer generation supersedes old pending events and retires old cursors.
It also persists a bounded fence for each retired computer generation;
attempting to bind that generation again is refused, even after restart or
terminal-event pruning. Retired fences count together with current bindings
and cursors against the existing 2,000 scope-record allowance, so the store
refuses a full fence capacity instead of evicting history. Retained cursors
fence duplicate revisions within the current generation, and strict load
validation rejects impossible event/cursor relationships, including pending
events from retired generations and multiple outcomes for one task generation.
Terminal records are kept for 7 days after acknowledgment. The hub prunes older
ones after recording proactive outcomes, and an admission at the 10,000-record
bound first drops them rather than refusing; retained evidence is never
evicted. Retired fences and cursors remain available to prevent replay.

Disabled instances perform no filesystem I/O or timer work. This module has
no timer and no runtime application path in this increment.

## Follow-up slices

Later work must separately define durable model jobs and their budgets,
outbox/receipt semantics, quiet-hour and presentation policy, approval and
user-priority behavior, and any settings or memory authority. Those slices
must not infer that an admitted lifecycle event was delivered merely because
this inbox persisted it.
