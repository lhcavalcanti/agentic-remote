# App settings

The category preview preserves the shell's hub-wide Display name field in App and moves existing scheduler permission defaults into a Scheduler category when the scheduler preview is available. The legacy layout keeps its existing placement. Remote machines offers Open Host monitor only when that preview is effective; it closes Settings and opens the existing monitor view.

The independent, default-off `skillToggles` preview adds Skills in both layouts. It lists text frontmatter from `~/.copilot/skills`, `~/.agents/skills`, `$COPILOT_HOME/skills` when different, configured `skillDirectories` (individual skills or containers), and `.github/skills` in the owning computer's known current/history session folders and their enclosing repositories. Configured and repository folders must pass the existing allowed-roots validation; repository roots and skill files cannot escape through symlinks. Discovery is bounded and never executes skill content or starts a CLI.

No existing CLI settings reader/writer was present, so the file is **`$COPILOT_HOME/settings.json`**, falling back to **`~/.copilot/settings.json`**. `disabledSkills` is keyed by skill name, including duplicate names from different locations. A change requires an explicit confirmation that it affects every CLI session on that computer; existing sessions may need to reload skills. The server requires that acknowledgement and a current content revision, preserves unrelated JSON keys and unknown disabled names, serializes writes, fsyncs a same-directory owner-only staging file and atomically renames it. It refuses corrupt/non-object JSON and symlink targets instead of repairing or replacing them. It checks for external edits immediately before replacement; a non-cooperating external writer must still be coordinated outside this app.

`GET/PATCH /api/computers/:computerId/skills` uses the shared Host/Origin guard. Authenticated `GET/PATCH /node-api/skills` rejects browser Origins, and the hub requires the node's versioned `skillSettings` capability before either read or write. Older nodes show “Update this computer”; offline nodes remain unavailable. This is on-demand, explicitly confirmed user configuration, not an autonomous service, so no additional hub flag is used. Preview off adds no UI or config reads/writes. Repository files are never modified; installation and removal are not supported.

The independent, default-off `healthCard` preview adds a read-only Health card to App in either settings layout. `/api/diagnostics/health` is covered by the shared Host/Origin guard and returns current-process startup records (bounded to 256), identity, an existing static build ID when available, the hub's paired-computer version/connection knowledge and effective hub flags. It performs no shell commands, provider starts or disk-log reads. Missing or older computer versions and unavailable timings are explicit; this is not an offline doctor or a history of prior process starts. The card names the separate `agentic-remote doctor` and `agentic-remote logs --why` commands but does not execute them.

The default-off `settingsNavigation` preview replaces the jump bar with searchable categories and a content pane. Phones use a category list followed by a page with an All settings button. Category buttons support Up/Down/Home/End; Escape keeps the app's existing topmost-dialog close behavior. Section scope labels distinguish hub-wide settings from this device. Search matches category and field labels and hides nonmatching cards without writing settings.

Remote machines embeds the same pairing/removal body as the legacy Computers dialog, adds the hub's online state, role and reported version, and refreshes connection status without starting processes. Manage computers deep-links here while the preview is enabled. Rename is not exposed because the existing API has no rename operation; a name can be supplied when pairing. Preview off preserves the original dialog and category order.

`AppSettingsDialog` renders the existing single scrolling dialog when settingsNavigation is off. `settingsSections` supplies the same Models, Folders, Oracle, Notifications, Interface, and App order to both its jump bar and its content. `scrollSettingsTo` scrolls only that dialog, moves heading focus on navigation, and follows Oracle's initial section while catalogs load until the user takes over scrolling.

Each `SettingsSection` declares `id`, `title`, `icon`, `scope`, and `render(props)`. The scope records the section's primary ownership:

- Models, Folders, Oracle, and Interface: `hub`.
- Notifications (permission and push subscription) and App (connection and updates): `device`.

Interface retains device-local keyboard shortcuts, and App still shows the hub's sync status. Oracle's own model and folders remain in its existing hub-owned manager settings, not the settings profile. Existing per-control scope labels remain unchanged; registry icons and scope metadata appear only in the preview category layout.

`App` still owns the settings-profile client and passes its current values, state, and callbacks to the dialog. Profile revisions, persistence, offline handling, and conflict resolution are unchanged. The shared status-line controls and runtime defaults are also used by the existing session UI. Runtime presentation helpers and default-runtime types have a single owner in `src/session-setup/`; settings imports those canonical exports.
