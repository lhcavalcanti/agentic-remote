# App settings

Category navigation preserves the shell's hub-wide Display name field in App and places scheduler permission defaults in a Scheduler category when the scheduler preview is available. Remote machines offers Open Host monitor only when that preview is effective; it closes Settings and opens the existing monitor view.

Skills is a standard settings category. It discovers personal skills in `$COPILOT_HOME/skills` (default `~/.copilot/skills`) and `~/.agents/skills`, all three project roots (`.github/skills`, `.agents/skills`, `.claude/skills`) at every level through each known repository, `skillDirectories`, comma-separated `COPILOT_SKILLS_DIRS`, installed plugin skills as `plugin:skill`, and cached built-ins under `$COPILOT_CACHE_HOME/pkg/<platform>/<version>/builtin`. Cache defaults are `~/Library/Caches/copilot` on macOS, `%LOCALAPPDATA%/copilot` on Windows, and `$XDG_CACHE_HOME/copilot` or `~/.cache/copilot` elsewhere, independently of `$COPILOT_HOME`. Discovery prefers the executable's cached version when identifiable; otherwise it selects the newest complete stable version numerically (or newest preview when no stable version is complete). Older install-relative layouts remain a fallback. A custom Copilot home replaces the default personal root; personal `~/.claude/skills` is not read. `ignoredSkillsLocations` excludes directories and their descendants, including canonical aliases. Configured and repository folders retain allowed-root and symlink containment checks. Discovery is bounded and never executes a skill or starts the CLI.

The only writable file is **`$COPILOT_HOME/settings.json`**, falling back to **`~/.copilot/settings.json`**. `disabledSkills` matches names case-insensitively, including plugin-qualified names. Trusted repositories can also disable a name in `.github/copilot/settings.json` or `settings.local.json`; these restrictions are additive and cannot be overridden by a user-file toggle. `ignoredSkillsLocations` comes only from user settings; unsupported repository-level values are ignored, including their types. The computer-wide view conservatively applies supported disable restrictions from every known permanently trusted repository. Session-only trust, ephemeral plugin directories, remote skills, and nonstandard CLI packaging cannot be inferred. Relative custom paths are skipped with a warning; ambiguous relative exclusions require a manual absolute or `~/` path instead of risking ineffective toggles.

SKILL.md must contain supported text frontmatter with a required name (the CLI alphabet, at most 64 characters) and description (at most 1024). Invalid or unsupported frontmatter, untrusted repository skills, repository-disabled names, and plugin names hidden by a blanket bare-name disable remain visible with a reason and no toggle. Unsupported names use stable schema-valid identifiers derived from their locations, so one bad file cannot invalidate the whole snapshot; its source location and validation reason remain visible. The app does not grant CLI folder trust or alter repository settings.

A change requires explicit confirmation of its computer-wide CLI effect and a current content revision. Files are decoded as strict UTF-8: invalid encoding is reported as unreadable and refuses a toggle without rewriting any bytes. Valid non-ASCII text and a leading UTF-8 BOM are preserved. JSONC comments and trailing commas are accepted. Array edits insert or remove only the confirmed skill's string tokens and separators, preserving every unrelated duplicate, order, original spelling, comment and byte. Disabling adds the name only when absent; enabling removes only its case-insensitive matches. Duplicate `disabledSkills` object keys still require manual repair. Writes retain unknown disabled names, serialize, fsync an owner-only staging file, and atomically rename it. Corrupt/non-object settings and symlink targets are refused. An external edit is checked immediately before replacement; a non-cooperating writer must still be coordinated outside this app.

`GET/PATCH /api/computers/:computerId/skills` uses the shared Host/Origin guard. Authenticated `GET/PATCH /node-api/skills` rejects browser Origins, and the hub requires the node's versioned `skillSettings` capability before either read or write. Capability version 2 is required so older nodes cannot silently omit manageability restrictions. Older nodes show “Update this computer”; offline nodes remain unavailable. This is on-demand, explicitly confirmed user configuration, not an autonomous service, so no additional hub flag is used. Config reads occur when Skills is opened, and writes require confirmation. Repository files are never modified; installation and removal are not supported.

App includes a read-only Health card by default. Searching for Health routes directly to the App card. `/api/diagnostics/health` is covered by the shared Host/Origin guard and returns current-process startup records (bounded to 256), identity, an existing static build ID when available, the hub's paired-computer version/connection knowledge and effective hub flags. It performs no shell commands, provider starts or disk-log reads. Missing or older computer versions and unavailable timings are explicit; this is not an offline doctor or a history of prior process starts. The card names the separate `agentic-remote doctor` and `agentic-remote logs --why` commands but does not execute them.

Settings uses searchable categories and a content pane. Its category order is Models, Folders, Remote machines, Oracle, Notifications, Interface, Skills and App, with Scheduler inserted after Notifications when its preview is effective. Phones use a category list followed by a page with an All settings button. Category buttons support Up/Down/Home/End; Escape keeps the app's existing topmost-dialog close behavior. Section scope labels distinguish hub-wide settings from this device. Search matches category and field labels and hides nonmatching cards without writing settings.

Remote machines embeds the pairing/removal body, shows the hub's online state, role and reported version, and refreshes connection status without starting processes. Any computer snapshot (Check connection, reconnect or startup) that authoritatively observes an unpaired computer, and the local Remove action, discard its sessions, task cache, side answers and drafts too; a newer computer event (such as a re-pair) keeps the computer, a newer session event alone does not, and older responses cannot restore removed state after a re-pair. Manage computers always deep-links here. Rename is not exposed because the existing API has no rename operation; a name can be supplied when pairing.

`AppSettingsDialog` always renders `SettingsNavigation` using `navigableSettingsSections`, with Skills and the effective Scheduler section inserted before rendering. Deep links select the owning category, including Oracle's model and Remote machines.

Each `SettingsSection` declares `id`, `title`, `icon`, `scope`, and `render(props)`. The scope records the section's primary ownership:

- Models, Folders, Remote machines, Oracle, Interface, Skills, and Scheduler: `hub`.
- Notifications (permission and push subscription) and App (connection and updates): `device`.

Interface retains device-local keyboard shortcuts, and App still shows the hub's sync status. Oracle's own model and folders remain in its existing hub-owned manager settings, not the settings profile. Existing per-control scope labels remain unchanged; registry icons and scope metadata appear in category navigation.

`App` still owns the settings-profile client and passes its current values, state, and callbacks to the dialog. Profile revisions, persistence, offline handling, and conflict resolution are unchanged. The shared status-line controls and runtime defaults are also used by the existing session UI. Runtime presentation helpers and default-runtime types have a single owner in `src/session-setup/`; settings imports those canonical exports.
